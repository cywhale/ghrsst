## Operator policy: a readiness collection is valid for two hours

**Policy.** Every figure in a readiness collection — free space, `latest`, healthz, lock state,
identity, manifest, WAL/anchor, quiescence — is valid for **2 hours from `measured_utc`**, and
only for the run that carries it. `ops/p5_readiness.MAX_CAPACITY_AGE_S` is that policy in
executable form; the code refuses stale evidence rather than relying on anyone remembering this
paragraph.

**Why two hours and not a day.** The ingest windows are 05:05, 07:30, 09:40, 18:05 and 20:30
local — gaps of roughly two to eight hours. A window longer than the shortest gap would let a
reading survive a schedule tick, which is precisely the event that invalidates it. Two hours is
long enough for one working session and short enough that no tick hides inside it.

**What invalidates a collection early**, regardless of the clock:

| event | what it moves |
|---|---|
| a daily or delta append | free space, `latest`, `delta_day_count`, lock mtimes |
| a service restart | pid, RSS, route, possibly the store being served |
| a mount or volume change | the device the whole capacity gate is about |
| any write under `$G` | everything the manifest and WAL requirements inspect |

**The operator rule.** Before a first compaction, re-confirm **all** of capacity, `latest`,
healthz, locks, P5 identity, manifest, WAL/anchor and quiescence **in one short window**, on the
host. Confirming them hours apart produces a report that is true of no single moment — the
defect this whole phase has been correcting, in its operational form.

**What the code enforces**, so the policy cannot be quietly ignored:

- `capacity.run_id` must equal the collection's `run_id`; both fields are **required**, and an
  absent one is `NOT_ADJUDICATED` rather than skipped.
- `measured_utc` must sit within 300s of `collected_utc` — they are meant to be one act.
- A reading more than 60s ahead of the assessing clock is refused: one that cannot be aged can
  never expire.
- The lock acquisition probe is bound to the declared lock by realpath, and to the run, host,
  time and actor. A probe of another path, run, host or sitting cannot produce `READY`.
- Every filesystem-backed requirement is `NOT_ADJUDICATED` off the host that owns the paths.

## What "the deployment" means: three stages, measured by running them

`identity` compares a deployment against a declared module inventory. That inventory used to be
the import closure of four entry points — `ingest.build_block`, `ingest.publish_manifest`,
`store.compaction_lock`, `api.app` — and importing a module is not running a lifecycle.

Three of this lifecycle's dependencies are **function-local imports**, invisible to any
import-only probe:

| where | imports | on which path |
| --- | --- | --- |
| `ingest/build_block.py` | `ingest.corrected_day` | the WAL repair-attestation branch |
| `ingest/swap_delta.py` | `ingest.corrected_day` | §7.5a re-authorization, under the lock |
| `ingest/corrected_day.py` | `ingest.publish_manifest` | the §7.8 refold |

A deployment could therefore be missing `ingest/corrected_day.py` outright, import all four
entry points cleanly, read `READY`, and fail at the first repair it tried to fold — with the
store half-changed. Worse, `ingest/prune_delta.py` and `ingest/swap_delta.py` — the half of the
lifecycle that **deletes days** — were named by nothing at all.

So the runtime is now declared as three stages, and each is measured by **executing** it against
the exact target commit, materialized from git blobs into a throwaway tree:

| stage | entry points | modules | how it is measured |
| --- | --- | --- | --- |
| `build` | `ingest.build_block`, `ingest.publish_manifest`, `store.compaction_lock` | 10 | a real fold with the WAL and anchor enabled, which attests a committed repair |
| `prune_swap` | `ingest.prune_delta`, `ingest.swap_delta`, `ingest.corrected_day` | 16 | a §7.8 refold, the §7.5a eligibility gate, a real prune with its validation, and a swap plan **actually executed** |
| `api` | `api.app` | 12 | import alone — `api/app.py` wires its routers at import, so there is no lazier surface to reach, and claiming a smoke here would be claiming evidence that does not exist |

Union, and the deployment's identity inventory: **23 modules**. The API stage stays a separate
declaration because it fails separately, and is unioned in because `api_parity` is a readiness
requirement.

The smokes run entirely inside `mkdtemp` in the materialized tree's own process, against a
synthetic 32×32 store built by that commit's own fixtures. They touch no store, no `$G` path and
no environment root. The one module they import that a deployment need not ship —
`tests/p5_fixtures.py`, which fabricates the inputs — is excluded by name, not by a blanket
exemption for `tests/`.

The match is required **in both directions**. A module the stage runs and the inventory does not
declare is a hole; a module the inventory declares and the stage never runs is a check that
cannot fire. Either one refuses.

### A separate blocker: no approved commit carries a PRODUCTION provisioning tool

**Corrected 2026-08-25.** `DEPLOYMENT_TOOLS` used to name `ops/p5_provision.py`, and the gate
read its presence as "this deployment can provision production". It cannot. That module refuses
any stage root inside the declared live root — deliberately, and the refusal must not be made
optional — and it declares its anchor with `allow_same_filesystem=True`, which is right for a
throwaway root on one filesystem and invalid for a deployment whose anchor is supposed to
outlive that filesystem. **A tool that refuses the job is not the tool for the job**, and the
gate was measuring the wrong thing.

So there are now two tools, named separately:

| declaration | module | what it can do |
|---|---|---|
| `DEPLOYMENT_TOOLS` | `ops/p5_prod_provision.py` | provisions the P5 roots **under the live root**, under an explicit production-scoped approval |
| `STAGING_TOOLS` | `ops/p5_provision.py` | provisions an **isolated** throwaway root; refuses the live root; not gated on |

`ops/p5_prod_provision.py` is a separate module rather than a flag, because a flag would make
the isolation guarantee optional and an optional guarantee is not one. It refuses, before
writing anything: an approval that is absent or not for this live root and this run; lock paths
that are not the canonical production ones, compared by `realpath` so an alias to the right
inode is accepted and one pointing away is not; an anchor that is inside the live root, on the
live root's device, undeclared, or carrying the same-filesystem waiver; P5 roots that already
exist — it neither adopts nor deletes them; free space below the **canonical** G18 floor, read
from `ops/p5s8_evidence.py` exactly as `p5_readiness` reads it, with a caller-supplied figure
refused unless it equals that value; and a compaction already running. Capacity and device are
re-measured **under the lock**, because a binding taken before the lock is a binding to a
different moment.

#### What it does: roots, generation 1, and the WAL bound to it

An earlier version published a block built from the **delta**. That would have been an invalid
authority: `api/app.py` treats a configured manifest as *the* base — `if mf_dir:
SegmentedCubeStore(mf_dir)` — and deliberately does not fall back to the monolith beside it.
Production delta holds ~58 days; the monolith holds 1 331. A generation 1 whose only segment
came from delta would have dropped roughly **1 273 days** of history from the served view the
moment it was configured, under a `/healthz` that still answered.

The version after that published nothing, which left a manifest root nothing could bind a WAL
to: `initialize_wal()` binds through `block_manifest.load_live()` and raises when nothing is
published. So "roots plus WAL, no manifest" was never reachable either.

The valid shape, and what the operation now does under §7.1b ordering:

```
flock(p5_compaction.lock)  ->  create p5_blocks and p5_repairs
   ->  PREPARE generation 1        <-- the expensive audit, ingest lock NOT held
        inspect_store_contract() + content_ledger() over the whole monolith
   ->  acquire ingest lock  ->  assert compaction lock still held
        ->  final cheap validation (metadata only)  ->  publish  <-- authority changes here
   ->  release ingest lock
   ->  initialize the WAL against that manifest and the external anchor
   ->  release compaction lock
```

**The preparation used to run inside the ingest lock.** Instrumentation showed both store
inspections *and* the whole-store file walk with the lock held — on a ~2 TB monolith that is
minutes of `stat` calls during which the daily-append cron is blocked behind a scan that has
nothing to do with it. The ingest lock exists to exclude ingest from the moment the store's
authority **changes**, and that moment is the publish.

So the builder is split: `prepare_generation_one()` does the audit and assembles the manifest,
`publish_prepared()` validates once more and publishes. Only the second is inside the lock, and
an event-order test asserts the ledger and the inspections run with the lock **not** held while
the publish runs with it held.

The split opens a window in which the monolith could change between preparing and publishing.
`validate_prepared()` closes it with a **cheap** re-check — metadata fingerprint, day digest,
layout and the seal barrier, all `O(arrays)` rather than `O(files)` — deliberately not the
content ledger, which is the expensive walk the split exists to keep out of the lock. What the
ledger cannot re-verify in that window is covered by the monolith being sealed.

`monolith_path` is required, not optional: a provisioner that might or might not publish is two
operations wearing one name.

**It does NOT switch `GHRSST_BLOCK_MANIFEST_DIR`.** Provisioning the roots and pointing the
service at them are different production changes with different blast radii. The deployment must
also name the monolith in `GHRSST_ALLOWED_LEGACY_PATHS` before the published manifest can be
served at all — the manifest does not authorize its own external path.

**This has only ever run in a local synthetic fixture.** Running it against `$G` publishes a
manifest and writes a WAL into production, and is a separate production operation requiring
explicit approval that has not been requested.

## The critical path

Each step is gated by the one before it, and none of them is code:

```
1. IT mount-layout decision        the monolith on its own read-only mount,
                                   beside writable P5 roots / WAL / delta
2. fresh VM24 read-only collection every readiness figure expires in 2 hours
3. candidate deployment review     a commit carrying the production tools
4. provisioning approval           production-scoped, naming the live root and run
5. provision generation 1 + WAL    roots, legacy_base manifest, WAL bound to it
6. API switchover approval         GHRSST_BLOCK_MANIFEST_DIR + the runtime allow-list
7. compaction approval             and only then a first fold
```

**Step 1 is not a formality, and it blocks everything after it.** The requirement handed to
storage, and the read-only checklist that establishes whether it has been met, are in
[`p5_monolith_mount_barrier_requirement.md`](p5_monolith_mount_barrier_requirement.md).

#### The one-shot exception is a detour around step 1, and only step 1

A human has accepted the risk of running **one** compaction before that mount layout exists,
because VM24 has full automated VM backups. It changes exactly one thing about the path above:
step 7 may be reached once without step 1. Steps 2–6 are untouched, and each still needs its own
approval.

It is a **record**, not a flag — bound to one host, one run, one monolith at one measured state,
one verified backup and one expiry — and it is reported in its own field,
`one_shot_compaction_exception`. It never makes `monolith_barrier` READY and never makes
`compaction_ready` true; an eligible exception beside a `BLOCKED` barrier is the expected shape.
The backup makes a failure **recoverable**, not unlikely, and restoring it rolls back the whole
machine, loses delta days and WAL repairs in the interval, and cannot recall answers already
served. §6a of the requirement document holds the binding table, the pre- and post-compaction
checks, and the full rollback limits. **The read-only mount remains the preferred route**, and
step 1 stays on the critical path for every run after this one.

The monolith is
`$G/mur_timecube_s8_t90_sh128.zarr`, and `$G` is on `/dev/sdc1` mounted at
`/home/odbadmin/Data`. The delta lives on that mount and the P5 roots would. Making it
read-only would freeze the delta and the WAL along with the monolith, leaving a deployment that
can neither ingest nor repair nor compact — so the barrier requires the monolith to be moved to,
or bind-mounted on, a **separate** read-only mount. That is a storage decision for whoever owns
the volumes, not a change this project can make.

The `monolith_barrier` requirement adjudicates a collected record of that layout:

| what it refuses | why |
|---|---|
| no record | missing evidence, `NOT_ADJUDICATED`, still blocks |
| mount options that are not read-only | `chmod` is not the barrier |
| a writable role on the SAME mount as the monolith | a mount is read-only or it is not; the two cannot both hold |
| a missing writable role (`p5_blocks`, `p5_repairs`, `delta`) | an unrecorded role is one nobody checked |
| a symlinked monolith, or a changed realpath | a link can be re-pointed without the record changing |
| another run, another host, stale, or future-dated | a mount can be remounted at any time |

Read-only is matched **by option token**, never by substring: `relatime` contains the letters
`ro`, and a substring test would call a writable mount frozen.

#### The monolith must be sealed BEFORE it becomes an authority

`immutable: true` in the segment is a declaration, and it is not treated as proof of anything.
`check_monolith_sealed()` is the check that stands behind it: it refuses a monolith whose store
root still carries write bits, before any manifest describes it, and records what it observed.

It is **necessary, not sufficient**, and says so where it is defined: it reads the store root's
permission bits only. A subdirectory could carry different ones, a process running as root
ignores permissions entirely, and a filesystem remounted read-write later changes the answer
without changing the record. **The barrier that would settle it is a read-only mount, which is a
deployment prerequisite this code cannot arrange** — so production readiness stays blocked on it
rather than being inferred from `immutable: true`.

#### The monolith is not sealed by the fingerprints alone

The design calls the monolith "immutable, NEVER rebuilt" (§4) — an intention about how the
deployment is operated, not something any code enforces. So the question is what the read path
notices, and it was measured rather than assumed:

| change to the monolith after generation 1 | detected? | by what |
|---|---|---|
| a day appended or removed | yes | metadata fingerprint / day digest |
| array layout, grid or axes changed | yes | layout and metadata fingerprint |
| **a value rewritten in place inside an existing day** | **no** | nothing — it was served silently |

The third row is the gap: neither fingerprint covers chunk bytes, so the manifest went on
describing a store that no longer held what it said. `content_seal` closes it — a ledger digest
over every file's path, size and mtime, recorded at build time and verified by
`SegmentedCubeStore` at construction.

**It is change detection, not a cryptographic seal**, and the code says so where it is defined.
Hashing ~2 TB of chunk bytes at every service start is not available — which is exactly why the
segment fingerprints are metadata-only. It catches a store that was written to; it would not
catch a forgery that restored size and mtime, and a test demonstrates precisely that limitation
by rewriting a byte in place and restoring both. A true seal is an operational control (a
read-only mount) and remains a deployment prerequisite.

#### The block grid is policy, and S is still provisional

`block_grid.block_days` is **S**, and there is no canonical S in the code to derive it from: the
design carries `S = 90 / C = 30` as prose, and the generated blockers table says it is
"provisional only; nothing has selected it". So it is one named constant,
`p5_legacy_base.BLOCK_DAYS_S`, declared as policy and read by the builder, with a test binding
the generated manifest to it. `BLOCK_DAYS_S_IS_PROVISIONAL` records that nothing has selected
90 over any other value.

The manifest schema has no field for "this number is policy", so the generated manifest says it
in `created_by`: *"block_days=90 is POLICY (BLOCK_DAYS_S), not derived from the store, and
PROVISIONAL: nothing has selected it"*. A reader of the artifact should not have to guess which
numbers were measured. **S = 90 / C = 30 is not selected**, and nothing here treats it as
selected; that would need an explicit operator decision recorded in the roadmap, and there is
none.

Two values that ARE derived, per design §12 M0, and were wrong when hardcoded:

* `block_grid.anchor_day` is **the day after the audited `end_day`** — the calendar grid starts
  where the legacy base stops, so the first future block abuts it instead of overlapping it. It
  had been the monolith's *first* day.
* `gaps` is `calendar[start..end] − present`. It had been `[]`, which would have claimed a
  contiguity the store may not have — and nothing downstream would catch it, because the day
  digest is computed over the days that ARE there and matches either way.

#### Interruption: recoverable, not atomic

Provisioning is **not atomic** and does not claim to be. What it guarantees is that whatever
write did not happen, the surviving record names every path that may exist. The marker declares
`planned_paths` **before anything is created** — the set is two fixed names under one root, so it
is knowable in advance — and `created_paths` grows as they really appear. The difference between
those lists is exactly the interruption window, and recovery takes the union. `contested_paths`
records a root that appeared under the lock, which this run did not create and must not remove.

`_write_marker()` fsyncs the file *and* the directory after the rename, because the protocol
rests on the marker being there afterwards.

**Operator recovery:** read `<live_root>/.p5_prod_provision_<run_id>.json`. If `complete` is
true there is nothing to undo. Otherwise pass that object to `rollback_production()`. If it
raises `ProductionCleanupError`, its `unrestored` list names the paths it could not remove and
the marker is deliberately kept — remove those by hand, then re-run to clear the marker. Never
delete the marker while a path it owns still exists.

#### Empty roots move nothing

The two directories are a precondition, not evidence. `manifest`, `blocks` and `wal_anchor` all
keep refusing until a valid generation 1 and an initialized WAL exist, and tests pin that.
Provisioning roots is not progress toward `compaction_ready`.

### Generation 1 over the monolith: the runtime path, and the builder

An earlier round found that a `legacy_base` generation 1 could not be served at all:
`api/app.py` constructed `SegmentedCubeStore(mf_dir)` with no `allowed_legacy_paths`, so a
segment pointing at the production monolith — a sibling of `p5_blocks`, therefore outside the
block root — was refused, and the service degraded to daily-only. **That blocker is closed.**

#### Two allow-lists, and they are not the same thing

| | where | what it does |
|---|---|---|
| **runtime** | `GHRSST_ALLOWED_LEGACY_PATHS`, read by `api.app.resolve_allowed_legacy_paths` | authorizes the **serving deployment** to follow a `legacy_base` segment out of the block root |
| **assessor** | `p5_readiness.ALLOWED_LEGACY_PATHS`, still `()` | what the **assessor** will accept in a manifest it is adjudicating, when reading collected evidence |

They answer different questions — "may this service read that store" and "may this manifest
claim that store" — and neither implies the other. Both fail closed when unset.

The runtime setting is validated before anything is served, and every way of getting it wrong is
a refusal rather than a skipped entry: not a string; an empty entry; a relative path; not an
existing directory; reached through a symlink (the store would accept the alias, but a reader of
the configuration cannot see where it points, and re-pointing the link would move what is
authorized without the configuration changing); or naming anything other than the monolith the
deployment already declares in `GHRSST_TIMECUBE_PATH`. **The manifest never authorizes its own
external path** — it names the path, and the deployment decides whether it may be followed.

When a manifest is configured and cannot be loaded, `/healthz` reports `status: "degraded"` with
`cube_error` and `manifest_configured: true`, and there is **no fallback to the monolith**. A
bare `ok` beside `cube_loaded: false` reads as "no cube configured", which is a different
deployment and the one nobody investigates. With no manifest configured the monolith fallback is
unchanged and the status stays `ok`.

#### The builder

`ops/p5_legacy_base.py` builds generation 1 over the existing monolith. Everything is derived
from `inspect_store_contract()` reading that store — day domain, variables, `var_valid` mode,
grid, layout and both fingerprints — and it publishes through `block_manifest.publish()`, which
validates and archives. There is no second manifest format and no second validator. The segment
path is relative, because an absolute one is refused outright.

Proved through the real read path, in an isolated fixture: every day and every variable matches
a `TimeCubeStore` oracle, first and last days included, with NaN preserved; the app's own
lifespan serves the monolith's values through the manifest; an under-declared manifest is
refused as `STALE MANIFEST` at construction rather than at the first request; and a delta-only
block cannot claim the legacy waiver.

It publishes into a manifest root it is given. It creates no roots, touches no WAL, and is
connected to neither `ops/p5_prod_provision.py` nor VM24. **Publishing a generation into a live
deployment is a production change with its own approval, and none has been requested.**

## The external approval record is a transcription, not a cryptographic signature

`assessor_is_approved()` binds an approval record to a commit. It requires the record to sit
**outside** the repository (checked through `realpath` as well as `abspath`, so a symlink cannot
smuggle it back in), to name this assessor's scope, to carry `approved_by` and a parsable
`approved_utc`, to name a SHA equal to the assessor's current `HEAD`, to find that worktree clean,
and to match every module in `ASSESSOR_MODULES` blob-for-blob at that commit.

What it does **not** establish is who wrote the file. Any process with write access to the
operator's home directory can produce one. On 2026-08-24 an unrelated session on the same machine
did exactly that, from a prompt pasted into the wrong window: the record it wrote for `7126c7b`
was correct in every field and passed every binding check above. That is the honest shape of the
mechanism — the guards held, and authorship was never among them.

So the record is an **operator transcription of a human decision, not a cryptographic
signature**, and this document says so rather than letting the phrase "approval record" imply
otherwise. The record for `7126c7b` is accepted on that basis.

The mechanism that would close the gap already exists and is unused: a record may carry
`signed_tag`, which the assessor verifies with `git verify-tag` **and** requires to resolve to the
approved commit. It needs a real signing key on the assessor host. Until there is one, no signed
tag is created — a fabricated signature would be worse than an acknowledged transcription.

### `3223fba` is retained, and this is the reasoning

It stays in `REVIEWED_DEPLOY_SHAS`. Recorded here because removing it would have changed what
that tuple means without saying so:

1. **Review is a historical fact.** `3223fba` completed review. Dropping it would assert
   something false about the past.
2. **The tuple is not only "may be deployed".** `_check_failure_semantics` reads it twice more —
   for which commits an executed result may be *read from*, and which deploy commit a recorded
   run may be *about*. Removing `3223fba` would retroactively invalidate every result ever
   recorded against it.
3. **Retention is not a loophole.** `deployment_tools` `BLOCKS` `3223fba` — and, since the tool
   split, `708058e` as well. Neither can reach `compaction_ready` however long either stays.

## `p5_shadow` is verification-only, and that is a real limit

`ops/p5_roadmap.py` declares the profile `scope: verification_only`: it proves a pre-provisioned
shadow is complete and safely placed, and takes no measurement. It cannot make a deployment
ready, because **it cannot create anything** — and there is nothing on VM24 for it to verify.

Calling it deployment-ready would repeat the error this phase has spent weeks correcting: a check
of one thing quoted as a verdict on another. So it is not called that anywhere, and
`ops/p5_provision.py` now exists to build what `p5_shadow` verifies:

- refuses a staging root inside the declared live root, **before creating anything**, by path
  components rather than string prefix;
- refuses a non-empty staging root, so rollback never has to guess what it made;
- `rollback()` removes exactly the root it created, refusing one without its marker, refusing one
  inside the live root, and idempotent when the root is already gone;
- builds blocks with `ingest.build_block`, publishes through `store.block_manifest`, initializes
  the WAL and anchor with `store.repair_wal` — **no second manifest, WAL or provenance format**;
- stamps the result `P5_ISOLATED_STAGING`, which `p5_readiness.NON_QUALIFYING_LABELS` refuses.
  A structurally perfect staging root can never read `READY`, because proving the recipe works is
  a different claim from a deployment being ready.

**No P5 state was created in `$G`, and this module will not create any.** Provisioning P5 roots
inside the live data root is a production change and needs its own explicit approval.

## What must be true before a first P5 compaction is safe

In dependency order. Each is reversible on its own.

1. **Land the P5 code as a reviewed deployment.** The live tree is `a9db4b7` plus uncommitted
   edits and contains none of the P5 store modules. Until a reviewed commit is deployed clean and
   detached, with a module inventory matching it, `identity` cannot leave `BLOCKED` — and every
   later step would be adjudicating unreviewed code.
2. **Reconcile the five uncommitted live modifications.** They are either wanted, in which case
   they belong in a reviewed commit, or unwanted, in which case the deployment has drifted.
   Nobody can say which from here; this needs the operator.
3. **Provision P5 roots** — `p5_blocks` with a published generation, `p5_repairs` initialized
   against that manifest authority, and an anchor declaring a rollback domain.
   `ops/p5_prod_provision.py` is the operation that does this **in production**;
   `ops/p5_provision.py` does it reversibly in an isolated root and refuses to do it here.
   Doing it in `$G` is a production change, needs its own production-scoped approval, and needs
   a deployed commit that carries the production tool — which no approved commit does yet.

   **This is machine-enforced, not a note.** The `deployment_tools` requirement adjudicates it:
   every entry in `DEPLOYMENT_TOOLS` must be present at the commit the target reports, and the
   digest the target reports for it must equal the digest recomputed from that commit's git
   blob. Absent tool, unreported digest, or mismatched digest are each `BLOCKED`. So a
   deployment that cannot run the provisioner cannot reach `compaction_ready`, and steps 3–5
   below cannot be reached by remembering to check something.

   It is a separate requirement from `identity` on purpose. `identity` asks whether the deployed
   bytes are the reviewed bytes; this asks whether the deployment carries the tool that creates
   what every store requirement then inspects. The reviewed `3223fba` predates the module
   entirely, so folding the two together would report one blocker as the other.
4. **Declare the anchor on a different failure domain.** The staging path uses
   `allow_same_filesystem=True`, which is correct for a throwaway root and wrong for a deployment:
   an anchor on the volume it witnesses is lost with it. A real deployment needs a declared
   external anchor location, which is an ops decision about hardware, not a code change.
5. **Stand up API route and value parity.** Either an isolated second service against the
   provisioned manifest, or a live switchover. Both need approval; the second also needs a
   rollback plan for the served view.
6. **Re-run this assessment on the host** and get `compaction_ready: true`. Nothing else
   substitutes: the artifact is generated on odb24 because filesystem checks mean nothing
   anywhere else.
7. **Obtain explicit approval for the first compaction itself.** A green readiness report is a
   precondition, never the authorization.

**The next minimal reversible step** is 1–2: get the P5 code onto VM24 as a reviewed, clean,
detached deployment and settle the uncommitted drift. Everything after it is blocked on that, and
neither requires touching `$G` or the served view.
